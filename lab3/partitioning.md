# Партиционирование

Пятый пункт задания является опциональным. Для текущей лабораторной базы партиционирование физически не требуется, потому что тестовый объём данных небольшой, но в реальном сервисе бронирования таблица `bookings` со временем станет самой крупной таблицей:
каждое бронирование создаёт новую запись, а старые брони обычно не удаляются, потому что они нужны для истории пользователя, отчётов и финансовой аналитики.

Поэтому для проекта выбрана стратегия партиционирования таблицы `bookings` по дате заезда `check_in`.

## Почему именно `bookings`

Таблица `bookings` подходит для партиционирования лучше остальных таблиц:

- `users` растёт медленно и обычно хорошо обслуживается обычными индексами;
- `hotels` и `rooms` являются справочными таблицами;
- `reviews` тоже могут расти, но они менее критичны для основной операции бронирования;
- `bookings` участвует в самых частых и дорогих запросах: проверка доступности номера, история броней, отмена бронирования, аналитика по периодам.

## Выбранная стратегия

Используется range partitioning по колонке `check_in`.

Пример:

```sql
PARTITION BY RANGE (check_in)
```

Партиции создаются поквартально:

```text
bookings_2026_q1: 2026-01-01 — 2026-04-01
bookings_2026_q2: 2026-04-01 — 2026-07-01
bookings_2026_q3: 2026-07-01 — 2026-10-01
bookings_2026_q4: 2026-10-01 — 2027-01-01
```

Поквартальное деление выбрано как компромисс. Месячные партиции дадут более точное отсечение данных, но увеличат количество таблиц. Годовые партиции проще, но хуже помогают запросам по коротким интервалам.

## Какие запросы выигрывают

### Проверка занятости номера

Основной запрос перед созданием бронирования:

```sql
SELECT EXISTS (
    SELECT 1
    FROM bookings
    WHERE room_id = $1
      AND status IN ('created', 'confirmed')
      AND check_in < $3
      AND check_out > $2
);
```

Если пользователь ищет номер на конкретные даты, PostgreSQL сможет отбросить часть партиций по `check_in` и не читать всю историю бронирований.

### Аналитика по периоду

Например, количество бронирований за квартал:

```sql
SELECT COUNT(*)
FROM bookings
WHERE check_in >= DATE '2026-04-01'
  AND check_in < DATE '2026-07-01';
```

При партиционировании такой запрос читает только нужную квартальную партицию.

### Архивация старых данных

Старые бронирования можно переносить или удалять целыми партициями. Это быстрее и безопаснее, чем удалять большое количество строк строк обычным `DELETE`.

## Индексы при партиционировании

Для партиционированной версии таблицы нужны те же логические индексы, что и для обычной таблицы:

```sql
CREATE INDEX idx_bookings_partitioned_user_id
    ON bookings_partitioned (user_id);

CREATE INDEX idx_bookings_partitioned_room_dates_active
    ON bookings_partitioned (room_id, check_in, check_out)
    WHERE status IN ('created', 'confirmed');

CREATE INDEX idx_bookings_partitioned_status
    ON bookings_partitioned (status);
```

Самый важный индекс остаётся частичным индексом по активным бронированиям:

```sql
WHERE status IN ('created', 'confirmed')
```

Он нужен потому что отменённые и завершённые бронирования не блокируют создание новой брони.

## Почему партиционирование не включено в основной `schema.sql`

В лабораторной работы используется обычная таблица `bookings`. Это сделано специально:

1. Текущий объём тестовых данных маленький.
2. Обычная таблица проще для первого запуска и проверки.
3. Основная цель лабораторной раюоты — показать корректную схему, индексы и запросы.
4. Партиционирование описано как масштабируемое развитие схемы.

SQL-пример находится в файле:

```text
db/partitioning.sql
```

Его можно использовать как проектное решение для production-версии системы.

## Итог

Для hotel booking сервиса наиболее разумно партиционировать таблицу `bookings` по дате заезда `check_in`. Такая стратегия ускоряет поиск и аналитику по периодам, упрощает архивирование старых бронирований и хорошо сочетается с уже созданным индексом для проверки пересечения дат.
