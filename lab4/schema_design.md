# Проектирование документной модели MongoDB

## Общая идея

Проект представляет собой сервис бронирования отелей. В предыдущем задании основная реляционная модель была реализована в PostgreSQL. В четвертой лабораторной работе MongoDB используется для тех частей системы, где документная модель удобнее реляционной:

- бронирования с историей изменений;
- отзывы с деталями пользователя и ответами отеля;
- пользовательские поисковые предпочтения;
- журнал событий бронирования.

Такой подход хорошо подходит для системы: часть данных остаётся строго структурированной, а часть хранится как документы с вложенными объектами и массивами.

## Коллекции

Для MongoDB проектируются следующие коллекции:

```text
bookings
reviews
user_preferences
booking_events
```

## Почему не переносим всё в MongoDB

Пользователи, отели и номера уже хорошо описываются реляционной моделью:

```text
users
hotels
rooms
```

Для них важны связи, уникальные ограничения и транзакционная целостность. Поэтому в MongoDB не нужно дублировать всю PostgreSQL-схему. Вместо этого MongoDB используется как документное хранилище для данных, которые естественно выглядят как документы.

---

# 1. Коллекция `bookings`

## Назначение

Коллекция хранит бронирования пользователей. В отличие от реляционной таблицы, документ бронирования содержит не только ID связей, но и snapshot-данные отеля и номера на момент создания брони.

Это важно, потому что название отеля, адрес, цена номера или тип номера могут измениться позже, но старая бронь должна отображаться пользователю в том виде, в котором она была создана.

## Пример документа

```json
{
  "_id": ObjectId("..."),
  "bookingId": "BK-2026-0001",
  "userId": "USR-0001",
  "hotelId": "HTL-0001",
  "roomId": "ROOM-0001",
  "status": "created",
  "period": {
    "checkIn": ISODate("2026-06-01T00:00:00Z"),
    "checkOut": ISODate("2026-06-04T00:00:00Z"),
    "nights": 3
  },
  "guests": {
    "adults": 2,
    "children": 0,
    "guestNames": [
      "Ivan Petrov",
      "Anna Petrova"
    ]
  },
  "hotelSnapshot": {
    "name": "Nevsky Palace",
    "city": "Saint Petersburg",
    "address": "Nevsky Prospect 10",
    "stars": 5
  },
  "roomSnapshot": {
    "roomNumber": "101",
    "roomType": "standard",
    "capacity": 2,
    "pricePerNight": 5200
  },
  "price": {
    "currency": "RUB",
    "pricePerNight": 5200,
    "totalPrice": 15600,
    "discount": 0
  },
  "payment": {
    "status": "pending",
    "method": "card"
  },
  "events": [
    {
      "type": "created",
      "message": "Booking was created",
      "createdAt": ISODate("2026-05-22T10:00:00Z")
    }
  ],
  "createdAt": ISODate("2026-05-22T10:00:00Z"),
  "updatedAt": ISODate("2026-05-22T10:00:00Z")
}
```

## Embedded documents

Внутри `bookings` используются embedded-документы:

```text
period
guests
hotelSnapshot
roomSnapshot
price
payment
events
```

### Почему embedded

Эти данные почти всегда читаются вместе с бронированием. Например, в личном кабинете пользователя нужно сразу показать:

- даты поездки;
- гостей;
- отель;
- номер;
- итоговую стоимость;
- статус оплаты;
- историю изменения бронирования.

Если хранить это в отдельных коллекциях, для одного экрана пришлось бы делать несколько запросов или aggregation с `$lookup`.

### Почему snapshot, а не только references

`hotelId` и `roomId` остаются references, но основные данные отеля и номера дополнительно сохраняются в snapshot.

Причина: бронь должна быть исторически стабильной. Если отель, например, поменяет название/категорию или номер станет дороже, старая бронь пользователя не должна измениться.

## References

В документе есть ссылки:

```text
userId
hotelId
roomId
```

### Почему references

Пользователь, отель и номер являются самостоятельными сущностями. Они могут участвовать в большом количестве бронирований. Полное встраивание пользователя или отеля в каждую бронь привело бы к лишнему дублированию.

# 2. Коллекция `reviews`

## Назначение

Коллекция хранит отзывы пользователей об отелях. Отзыв является отдельной сущностью, потому что:

- отзывы часто выводятся списком на странице отеля;
- отзывы могут модерироваться;
- отзыв может иметь ответ отеля;
- по отзывам можно строить рейтинг и аналитику.

## Пример документа

```json
{
  "_id": ObjectId("..."),
  "reviewId": "REV-0001",
  "userId": "USR-0001",
  "hotelId": "HTL-0001",
  "bookingId": "BK-2026-0001",
  "rating": 5,
  "comment": "Clean room and very good location.",
  "pros": [
    "location",
    "clean room",
    "friendly staff"
  ],
  "cons": [
    "small parking"
  ],
  "travelerType": "couple",
  "moderation": {
    "status": "approved",
    "checkedBy": "system",
    "checkedAt": ISODate("2026-05-22T11:00:00Z")
  },
  "hotelReply": {
    "message": "Thank you for your feedback!",
    "createdAt": ISODate("2026-05-23T09:00:00Z")
  },
  "createdAt": ISODate("2026-05-22T10:30:00Z")
}
```

## Embedded documents

Внутри `reviews` embedded используются для:

```text
moderation
hotelReply
pros
cons
```

### Почему embedded

Модерация и ответ отеля не являются саммостоятельными отдельно от отзыва. Они нужны только при чтении конкретного отзыва или списка отзывов.

`pros` и `cons` — массивы простых значений. Их удобно хранить прямо внутри документа.

## References

В документе используются ссылки:

```text
userId
hotelId
bookingId
```

### Почему references

Отзыв связан с пользователем, отелем и иногда с конкретным бронированием. Но эти сущности не нужно полностью встраивать в отзыв: пользователь и отель могут изменяться, а отзыв должен только ссылаться на них.

# 3. Коллекция `user_preferences`

## Назначение

Коллекция хранит поисковые и пользовательские предпочтения. Эти данные слабо структурированы и могут постепенно расширяться: любимые города, типы номеров, удобства, диапазон цены, история последних фильтров.

Для PostgreSQL такая структура была бы менее удобной, потому что пришлось бы создавать несколько вспомогательных таблиц.

## Пример документа

```json
{
  "_id": ObjectId("..."),
  "userId": "USR-0001",
  "favoriteCities": [
    "Saint Petersburg",
    "Moscow"
  ],
  "preferredRoomTypes": [
    "standard",
    "comfort"
  ],
  "amenities": [
    "wifi",
    "parking",
    "breakfast"
  ],
  "priceRange": {
    "min": 3000,
    "max": 9000,
    "currency": "RUB"
  },
  "lastSearch": {
    "city": "Moscow",
    "checkIn": ISODate("2026-06-10T00:00:00Z"),
    "checkOut": ISODate("2026-06-12T00:00:00Z"),
    "guests": 2
  },
  "updatedAt": ISODate("2026-05-22T12:00:00Z")
}
```

## Embedded documents

Внутри документа используются:

```text
priceRange
lastSearch
favoriteCities
preferredRoomTypes
amenities
```

### Почему embedded

Предпочтения почти всегда читаются и обновляются одним документом по `userId`. Они не требуют отдельных коллекций.

## References

Используется ссылка:

```text
userId
```

### Почему reference

Профиль пользователя хранится отдельно. Preferences — это дополнительный документ, связанный с пользователем.

# 4. Коллекция `booking_events`

## Назначение

Коллекция хранит расширенный журнал событий по бронированиям. Внутри `bookings.events` хранится короткая история, которая нужна для быстрого отображения пользователю. Но для аудита, аналитики и отладки лучше иметь отдельную коллекцию событий.

## Пример документа

```json
{
  "_id": ObjectId("..."),
  "eventId": "EVT-0001",
  "bookingId": "BK-2026-0001",
  "userId": "USR-0001",
  "type": "status_changed",
  "payload": {
    "oldStatus": "created",
    "newStatus": "confirmed",
    "source": "payment-service"
  },
  "createdAt": ISODate("2026-05-22T12:10:00Z")
}
```

## Embedded documents

Внутри события используется embedded-документ:

```text
payload
```

### Почему embedded

`payload` зависит от типа события и может иметь разную структуру. MongoDB подходит для такого сценария лучше, чем строгая реляционная таблица.

## References

Используются ссылки:

```text
bookingId
userId
```

### Почему references

Событий может быть очень много. Встраивать весь журнал в документ бронирования опасно: документ может сильно вырасти. Поэтому в `bookings.events` хранится короткая пользовательская история, а полный аудит — в отдельной коллекции `booking_events`.

---

# Итог по embedded и references

| Связь | Решение | Обоснование |
|---|---|---|
| Booking -> period | Embedded | Даты всегда нужны вместе с бронированием |
| Booking -> guests | Embedded | Список гостей относится только к конкретной брони |
| Booking -> hotelSnapshot | Embedded | Нужен исторический снимок отеля |
| Booking -> roomSnapshot | Embedded | Нужен исторический снимок номера и цены |
| Booking -> price | Embedded | Цена относится к конкретной брони |
| Booking -> payment | Embedded | Краткий статус оплаты нужен вместе с бронью |
| Booking -> events | Embedded частично | Короткая история нужна в карточке бронирования |
| Booking -> user | Reference | Пользователь самостоятельная сущность |
| Booking -> hotel | Reference + snapshot | Отель самостоятельная сущность, но нужен исторический снимок |
| Booking -> room | Reference + snapshot | Номер самостоятельная сущность, но нужна цена на момент бронирования |
| Review -> moderation | Embedded | Модерация относится только к отзыву |
| Review -> hotelReply | Embedded | Ответ отеля относится только к отзыву |
| Review -> user | Reference | Пользователь самостоятельная сущность |
| Review -> hotel | Reference | Отель самостоятельная сущность |
| UserPreferences -> user | Reference | Профиль пользователя хранится отдельно |
| BookingEvent -> booking | Reference | Событий может быть много, хранить их все в booking опасно |

## Вывод

MongoDB в этой лабораторной работе используется не как замена всей реляционной базы, а как документное хранилище для гибких и исторических данных. Основная коллекция — `bookings`, потому что бронирование естественно описывается одним документом: даты, гости, снимок отеля, снимок номера, цена, оплата и короткая история событий.

Такой дизайн уменьшает количество join-операций при чтении бронирования, сохраняет историческую корректность данных и хорошо подходит для подключения к API на userver через MongoDB-компонент.
