# Анализ производительности и стратегия оптимизации

## 1. Hot paths — часто выполняемые операции

Hot path — это участок системы, который вызывается часто и поэтому сильнее всего влияет на общую производительность.

Для hotel booking сервиса к hot paths относятся следующие операции.

### 1.1 Получение списка отелей

Endpoint:

```text
GET /hotels
GET /hotels?city=...
```

Почему это hot path:

- пользователь обычно начинает работу с поиска отелей;
- один пользователь может несколько раз менять город, фильтры и сортировку;
- список отелей читается намного чаще, чем изменяется;
- данные отелей относительно стабильны.

Типовая нагрузка:

```text
много READ-запросов
мало WRITE-запросов
```

Вывод:

```text
GET /hotels — главный кандидат на кеширование.
```

---

### 1.2 Поиск отелей по городу

Endpoint:

```text
GET /hotels?city=Moscow
```

Почему это hot path:

- поиск по городу — базовый сценарий booking-сервиса;
- многие пользователи могут искать одни и те же города;
- результат хорошо кешируется по ключу `city`.

Вывод:

```text
результаты поиска отелей по городу можно кешировать отдельно от общего списка.
```

---

### 1.3 Получение номеров отеля

Endpoint:

```text
GET /rooms?hotelId=...
```

Почему это hot path:

- после открытия страницы отеля пользователь смотрит номера;
- номера отеля меняются редко;
- цена, тип номера и вместимость читаются часто.

Вывод:

```text
GET /rooms?hotelId=... — второй хороший кандидат на кеширование.
```

---

### 1.4 Авторизация пользователя

Endpoint:

```text
POST /auth/login
```

Почему это hot path:

- логин вызывается часто;
- внутри происходит поиск пользователя по логину;
- операция чувствительна к безопасности.

Вывод:

```text
авторизацию не стоит кешировать как обычный endpoint, но её нужно защищать rate limiting от brute-force атак.
```

---

### 1.5 Создание бронирования

Endpoint:

```text
POST /bookings
```

Почему это hot path и одновременно critical path:

- операция важна для бизнеса;
- перед созданием брони нужно проверить доступность номера;
- операция меняет данные;
- возможны конкурентные запросы на один и тот же номер.

Вывод:

```text
POST /bookings не кешируется, но требует rate limiting и аккуратной работы с БД.
```

---

## 2. Потенциально медленные операции

Медленные операции — это операции, которые могут обращаться к базе данных, выполнять сложные проверки или создавать блокировки.

### 2.1 Поиск свободных номеров по датам

Endpoint:

```text
GET /rooms?hotelId=...&checkIn=...&checkOut=...
```

Потенциальная проблема:

- нужно проверить пересечение дат с существующими бронированиями;
- при большом количестве бронирований запрос может стать дорогим;
- запрос зависит от дат, поэтому кешировать его сложнее.

Причина медленности:

```text
NOT EXISTS / проверка пересечения интервалов по bookings
```

Оптимизация:

```text
индекс по room_id, check_in, check_out для активных бронирований
```

---

### 2.2 Создание бронирования

Endpoint:

```text
POST /bookings
```

Потенциальная проблема:

- операция пишет в БД;
- перед записью нужно проверить конфликт дат;
- возможна конкуренция за один номер;
- после создания брони нужно инвалидировать кеши, связанные с доступностью.

Почему не кешируется:

```text
это write-операция, результат зависит от текущего состояния бронирований
```

Оптимизация:

```text
rate limiting + индексы + транзакция + инвалидация кеша
```

---

### 2.3 Получение бронирований пользователя

Endpoint:

```text
GET /bookings
```

Потенциальная проблема:

- у активных пользователей может быть большая история бронирований;
- запрос требует фильтрации по user_id;
- в расширенной версии может включать JOIN с rooms/hotels.

Оптимизация:

```text
индекс по bookings.user_id
пагинация
ограничение размера ответа
```

---

### 2.4 Отзывы и агрегированные рейтинги

Endpoint'ы MongoDB:

```text
GET /mongo/reviews?hotelId=...
aggregation.js
```

Потенциальная проблема:

- отзывы могут быстро расти;
- средний рейтинг и аналитика требуют агрегаций;
- aggregation pipeline дороже обычного find.

Оптимизация:

```text
индекс по hotelId
кеширование агрегированного рейтинга
ограничение размера выборки
```

---

### 2.5 Внешние API

В текущей версии внешние API не используются. Но в production-версии booking-сервиса потенциально медленными внешними зависимостями были бы:

```text
платёжный сервис
email/SMS-уведомления
карты и геокодинг
внешние провайдеры отелей
```

Для таких операций нужны:

```text
timeouts
retries с ограничением
circuit breaker
асинхронная обработка
```

В рамках текущей лабораторной работы основной фокус — БД, кеширование и rate limiting.

---

## 3. Требования к производительности

Требования заданы как целевые ориентиры для учебного сервиса. Они не являются production SLA, но помогают обосновать кеширование и rate limiting.

### 3.1 Время отклика

| Операция | Целевое время без кеша | Целевое время с кешем | Комментарий |
|---|---:|---:|---|
| `GET /hotels` | до 150 мс | до 30 мс | часто читаемый список |
| `GET /hotels?city=...` | до 150 мс | до 30 мс | кеш по городу |
| `GET /rooms?hotelId=...` | до 120 мс | до 30 мс | номера меняются редко |
| `POST /auth/login` | до 150 мс | не кешируется | нужна защита от brute-force |
| `POST /bookings` | до 300 мс | не кешируется | запись + проверка доступности |
| `GET /bookings` | до 200 мс | опционально | зависит от истории пользователя |
| `DELETE /bookings` | до 200 мс | не кешируется | write-операция |

---

### 3.2 Пропускная способность

Ориентиры для одного учебного инстанса API:

| Тип endpoint'а | Целевой уровень |
|---|---:|
| Чтение отелей/номеров | 100-300 RPS |
| Авторизация | 30-60 RPS |
| Создание бронирования | 10-30 RPS |
| Отмена бронирования | 10-30 RPS |
| MongoDB reviews/bookings read | 50-150 RPS |

Кеширование должно разгрузить базу данных для read-heavy endpoint'ов. Rate limiting должен защитить write-heavy и security-sensitive endpoint'ы.

---

## 4. Риски производительности

### 4.1 Перегрузка базы данных

Если каждый `GET /hotels` и `GET /rooms` всегда ходит в PostgreSQL, то при росте количества пользователей база будет тратить ресурсы на повторяющиеся одинаковые запросы.

Решение:

```text
cache-aside кеширование для GET /hotels и GET /rooms
```

---

### 4.2 Перегрузка endpoint'а создания бронирования

`POST /bookings` может стать дорогим из-за проверки конфликтов и записи в БД. Кроме того, этот endpoint может быть целью автоматизированных запросов.

Решение:

```text
Token Bucket rate limiting
```

---

### 4.3 Устаревшие данные в кеше

Если создать новый отель или изменить номер, кеш списка отелей/номеров может стать неактуальным.

Решение:

```text
инвалидация кеша при POST /hotels
инвалидация кеша номеров/доступности при POST /bookings и DELETE /bookings
TTL как дополнительная страховка
```

---

### 4.4 Конкурентное бронирование одного номера

Два пользователя могут одновременно попытаться забронировать один номер на одни и те же даты.

Решение:

```text
проверка конфликта в транзакции
индекс по активным бронированиям
ограничение частоты POST /bookings
```

---

## 5. Вывод по первому пункту

Наиболее частые операции в системе:

```text
GET /hotels
GET /hotels?city=...
GET /rooms?hotelId=...
POST /auth/login
POST /bookings
```

Наиболее медленные или рискованные операции:

```text
поиск свободных номеров по датам
создание бронирования
получение большой истории бронирований пользователя
агрегации по отзывам и выручке
```

Для пятой лабораторной работы оптимизация будет направлена на два направления:

```text
1. Кеширование read-heavy endpoint'ов:
   - GET /hotels
   - GET /rooms?hotelId=...

2. Rate limiting critical endpoint'ов:
   - POST /bookings
   - опционально POST /auth/login
```

Такой выбор соответствует поведению hotel booking сервиса: пользователи часто читают каталожные данные, но создание бронирования должно быть защищено от перегрузки и автоматизированных запросов.

# Стратегия кеширования

## 1. Какие данные можно кешировать

В hotel booking сервисе кешировать нужно не все данные подряд. Кеширование подходит для данных, которые часто читаются, редко изменяются и не требуют строгой актуальности в каждую миллисекунду.

## 1.1 Часто читаемые данные

### Список отелей

Endpoint:

```text
GET /hotels
GET /hotels?city=...
```

Причина для кеширования:

- список отелей запрашивается часто;
- данные отелей меняются редко;
- одинаковые города часто ищут разные пользователи;
- запрос обращается к PostgreSQL и может выполняться много раз с одинаковыми параметрами.

Кешируемый результат:

```text
список отелей целиком
список отелей по городу
список отелей по городу и минимальному количеству звёзд
```

Пример ключей кеша:

```text
hotels:all:min_stars:1
hotels:city:Moscow:min_stars:4
hotels:city:Sochi:min_stars:5
```

---

### Список номеров отеля

Endpoint:

```text
GET /rooms?hotelId=...
```

Причина для кеширования:

- пользователь часто открывает страницу отеля и смотрит номера;
- номера отеля меняются редко;
- список номеров может быть одинаковым для большого количества пользователей.

Кешируемый результат:

```text
список номеров конкретного отеля
```

Пример ключа кеша:

```text
rooms:hotel:1
```

---

## 1.2 Результаты сложных вычислений

### Средний рейтинг отеля

Потенциальный endpoint:

```text
GET /mongo/reviews?hotelId=...
```

Или aggregation pipeline:

```text
aggregation.js
```

Причина для кеширования:

- средний рейтинг считается по отзывам;
- отзывы могут храниться в MongoDB;
- агрегация дороже обычного чтения одного документа;
- рейтинг не обязан обновляться мгновенно после каждого нового отзыва.

Кешируемый результат:

```text
averageRating
reviewsCount
ratingDistribution
```

Пример ключа кеша:

```text
hotel_rating:HTL-0002
```

В рамках минимальной реализации этот кеш можно описать как проектное решение, а в коде реализовать кеширование двух основных endpoint'ов: `GET /hotels` и `GET /rooms`.

---

## 1.3 Данные, которые редко изменяются

К редко изменяемым данным относятся:

```text
название отеля
город отеля
адрес отеля
количество звёзд
описание отеля
номер комнаты
тип номера
вместимость номера
базовая цена номера
```

Эти данные подходят для кеширования, потому что они не меняются при каждом пользовательском запросе.

---

## 2. Что не нужно кешировать

Некоторые данные кешировать опасно или бессмысленно.

### Авторизация

Endpoint:

```text
POST /auth/login
```

Причина:

- операция связана с безопасностью;
- результат зависит от пароля;
- неправильное кеширование может привести к уязвимостям.

Решение:

```text
не кешировать
использовать rate limiting
```

---

### Создание бронирования

Endpoint:

```text
POST /bookings
```

Причина:

- write-операция;
- меняет состояние системы;
- требует проверки доступности номера;
- результат должен быть актуальным.

Решение:

```text
не кешировать
после успешной записи инвалидировать связанные кеши
```

---

### Отмена бронирования

Endpoint:

```text
DELETE /bookings
```

Причина:

- write-операция;
- меняет статус брони;
- может повлиять на доступность номера.

Решение:

```text
не кешировать
после успешной отмены инвалидировать связанные кеши
```

---

### Поиск свободных номеров на даты

Endpoint:

```text
GET /rooms?hotelId=...&checkIn=...&checkOut=...
```

Причина:

- результат зависит от текущих бронирований;
- данные быстро устаревают после создания или отмены брони;
- высокий риск показать пользователю уже занятый номер.

Решение:

```text
на первом этапе не кешировать
при production-доработке можно кешировать на очень короткий TTL 10-30 секунд
```

---

## 3. Выбор стратегии кеширования

## 3.1 Cache-Aside для списка отелей

Выбранная стратегия:

```text
Cache-Aside / Lazy Loading
```

Алгоритм:

```text
1. Handler получает GET /hotels.
2. Формируется ключ кеша по параметрам запроса.
3. Сервис проверяет кеш.
4. Если значение найдено — возвращается ответ из кеша.
5. Если значения нет — сервис читает данные из PostgreSQL.
6. Результат сохраняется в кеш с TTL.
7. Ответ возвращается пользователю.
```

Почему Cache-Aside:

- простая реализация;
- подходит для учебного проекта;
- не требует менять слой базы данных;
- хорошо работает для read-heavy endpoint'ов;
- при падении кеша сервис может продолжить работать через БД.

TTL:

```text
60 секунд
```

Инвалидация:

```text
при POST /hotels удалить все ключи, начинающиеся с hotels:
```

---

## 3.2 Cache-Aside для списка номеров отеля

Выбранная стратегия:

```text
Cache-Aside / Lazy Loading
```

Алгоритм:

```text
1. Handler получает GET /rooms?hotelId=...
2. Формируется ключ rooms:hotel:{hotelId}.
3. Сервис проверяет кеш.
4. При cache hit возвращает список номеров.
5. При cache miss читает номера из PostgreSQL.
6. Сохраняет результат в кеш.
```

TTL:

```text
60 секунд
```

Инвалидация:

```text
при изменении данных номера удалить rooms:hotel:{hotelId}
при создании бронирования удалить rooms:hotel:{hotelId}, если известен hotelId
при отмене бронирования удалить rooms:hotel:{hotelId}, если известен hotelId
```

В текущем проекте endpoint изменения номера пока не реализован, поэтому основная инвалидация будет связана с бронированиями.

---

## 3.3 Read-Through

Read-Through означает, что приложение обращается к кешу как к основному источнику чтения, а сам кеш при промахе загружает данные из БД.

Для текущего проекта эта стратегия не выбрана.

Причина:

```text
потребовался бы отдельный кеширующий слой с логикой загрузки из PostgreSQL
для учебного проекта это избыточно
```

---

## 3.4 Write-Through

Write-Through означает, что при записи данные одновременно пишутся в БД и кеш.

Для текущего проекта эта стратегия не выбрана как основная.

Причина:

```text
создание отеля и бронирования выполняются намного реже чтения
проще и безопаснее инвалидировать кеш, чем пытаться обновить все возможные варианты списков
```

Например, при создании отеля нужно было бы обновить:

```text
hotels:all:min_stars:1
hotels:city:Moscow:min_stars:1
hotels:city:Moscow:min_stars:2
hotels:city:Moscow:min_stars:3
hotels:city:Moscow:min_stars:4
hotels:city:Moscow:min_stars:5
```

Это неудобно и легко приводит к ошибкам.

---

## 3.5 Write-Back / Write-Behind

Write-Back означает, что запись сначала попадает в кеш, а в БД сохраняется позже.

Для текущего проекта эта стратегия не подходит.

Причина:

```text
создание бронирования — критичная операция
нельзя подтверждать бронь пользователю до надежной записи в БД
при сбое кеша можно потерять данные
```

Вывод:

```text
Write-Back не используется для бронирований и пользователей
```

---

## 4. TTL для кешируемых данных

| Данные | Endpoint | TTL | Причина |
|---|---|---:|---|
| Список всех отелей | `GET /hotels` | 60 секунд | данные редко меняются |
| Отели по городу | `GET /hotels?city=...` | 60 секунд | частый повторяющийся поиск |
| Номера отеля | `GET /rooms?hotelId=...` | 60 секунд | номера меняются редко |
| Средний рейтинг отеля | aggregation/reviews | 5 минут | рейтинг не критичен к мгновенному обновлению |
| Свободные номера по датам | `GET /rooms?...&checkIn=...` | не кешируется | высокий риск устаревания |
| Авторизация | `POST /auth/login` | не кешируется | безопасность |
| Создание бронирования | `POST /bookings` | не кешируется | write-операция |

Для учебной реализации выбран короткий TTL 60 секунд, чтобы:

```text
снизить нагрузку на БД
не держать устаревшие данные слишком долго
упростить проверку работы кеша
```

---

## 5. Стратегия инвалидации кеша

## 5.1 Инвалидация при создании отеля

Endpoint:

```text
POST /hotels
```

После успешного создания отеля нужно удалить:

```text
все ключи hotels:
```

Причина:

```text
новый отель может попасть в общий список и в поиск по городу
```

---

## 5.2 Инвалидация при создании бронирования

Endpoint:

```text
POST /bookings
```

После успешного создания бронирования нужно удалить:

```text
rooms:hotel:{hotelId}
```

Если в будущем будет кешироваться доступность по датам, нужно будет удалить также:

```text
available_rooms:hotel:{hotelId}:*
```

В минимальной реализации достаточно инвалидировать кеш номеров отеля или полностью группу `rooms:`.

---

## 5.3 Инвалидация при отмене бронирования

Endpoint:

```text
DELETE /bookings
```

После отмены бронирования нужно удалить:

```text
rooms:hotel:{hotelId}
```

Если hotelId неизвестен в handler'е, допустимо удалить все ключи:

```text
rooms:
```

Для учебного проекта это нормально: инвалидация будет чуть грубее, но безопаснее.

---

## 5.4 Инвалидация по TTL

Даже если явная инвалидация не сработала, данные автоматически станут неактуальными после истечения TTL.

Это дополнительная защита от stale cache.

## 6. Выбранная реализация для проекта

Для пятого задания будет реализовано простое in-memory кеширование внутри API-сервиса.

Почему не Redis на этом этапе:

```text
требование разрешает Redis, но не обязывает его
один учебный API-инстанс проще и надежнее проверить
меньше инфраструктурных зависимостей
легче показать логику кеширования и инвалидации
```

Ограничение:

```text
in-memory кеш работает только внутри одного экземпляра API
при масштабировании на несколько инстансов лучше заменить его на Redis
```

Итоговая реализация:

```text
GET /hotels          -> Cache-Aside, TTL 60 секунд
GET /rooms?hotelId   -> Cache-Aside, TTL 60 секунд
POST /hotels         -> инвалидация hotels:
POST /bookings       -> инвалидация rooms:
DELETE /bookings     -> инвалидация rooms:
```

## 7. Метрики кеширования

Для анализа эффективности кеша нужно отслеживать:

```text
cache_hits_total
cache_misses_total
cache_hit_rate
cache_items_count
cache_evictions_total
average_response_time_before_cache
average_response_time_after_cache
database_queries_saved
```

Формула hit rate:

```text
cache_hit_rate = cache_hits / (cache_hits + cache_misses)
```

Для текущей реализации достаточно логировать cache hit/cache miss и сравнивать время ответа вручную через curl/Postman или простую нагрузочную утилиту.

# Проектирование rate limiting

## 1. Зачем нужен rate limiting

Rate limiting нужен, чтобы защитить API от:

```text
автоматизированных запросов
brute-force попыток авторизации
перегрузки базы данных
слишком частого создания бронирований
ошибок клиентских приложений с бесконечными retry
```

Для системы бронирования отелей особенно важно ограничивать операции, которые:

```text
изменяют состояние системы
обращаются к базе данных
требуют проверки доступности номера
связаны с авторизацией
могут быть целью перебора
```

---

## 2. Endpoints, которым нужен rate limiting

## 2.1 POST /bookings

Назначение:

```text
создание бронирования
```

Почему нужен rate limiting:

```text
операция пишет в БД
перед созданием выполняется проверка конфликта дат
создание брони может блокировать номер для других пользователей
endpoint может быть целью спама или ошибочных retry
```

Выбранный алгоритм:

```text

```

Почему Token Bucket:

```text
позволяет обрабатывать короткие всплески активности
не блокирует нормального пользователя при нескольких быстрых запросах
хорошо подходит для write endpoint'ов
легко объясняется и реализуется в API
```

Лимит для обычного пользователя:

```text
10 запросов в минуту
```

Burst:

```text

```

Premium-пользователь:

```text

```

В текущей реализации premium-роль можно описать проектно, но в коде использовать общий лимит.

```text
предотвращение массового перебора паролей
```

Почему Fixed Window Counter:

```text
простая реализация
хорошо подходит для учебного проекта

```

Лимит:

```text
5 попыток в минуту на login + IP
```

```text
защита от массового создания аккаунтов
снижение риска засорения базы тестовыми пользователями
```

Выбранный алгоритм:

```text
Fixed Window Counter
```

Ключ:


## 3. Сравнение алгоритмов

| Алгоритм | Где подходит | Плюсы | Минусы |
|---|---|---|---|
| Token Bucket | `POST /bookings` | допускает короткие burst, гибкий | чуть сложнее Fixed Window |
| Fixed Window Counter | `POST /auth/login`, `POST /auth/register` | очень простой | возможен всплеск на границе окна |
| Sliding Window Counter | публичные GET endpoints | более ровное ограничение | сложнее хранить состояние |
| Leaking Bucket | стабильная очередь запросов | сглаживает поток | хуже для пользовательских burst |

# Анализ влияния кеширования и rate limiting на производительность

## 1. Как кеширование улучшает производительность

Кеширование уменьшает количество повторных обращений к PostgreSQL для часто читаемых данных.

В проекте кешируются:

```text
GET /hotels
GET /rooms?hotelId=...
```

Эти endpoint'ы читают справочные данные: отели и номера. Такие данные запрашиваются часто, но изменяются редко. Поэтому их можно безопасно хранить в кеше короткое время.

## 1.1 Уменьшение времени ответа

Без кеша каждый запрос выполняет обращение к PostgreSQL:

```text
HTTP request -> handler -> PostgreSQL -> handler -> HTTP response
```

С кешем при повторном запросе цепочка короче:

```text
HTTP request -> handler -> in-memory cache -> HTTP response
```

Это уменьшает:

```text
сетевые обращения к БД
нагрузку на PostgreSQL
среднее время ответа
количество одинаковых SQL-запросов
```

## 1.2 Снижение нагрузки на базу данных

Для endpoint'а:

```text
GET /hotels?city=Moscow&minStars=4
```

без кеша 100 одинаковых запросов создадут 100 обращений к PostgreSQL.

С кешем:

```text
1 запрос -> PostgreSQL
99 запросов -> cache hit
```

При hit rate 99% база получает только один запрос вместо ста.

## 1.3 Устойчивость при пиках чтения

Если несколько пользователей одновременно ищут отели в одном городе, кеш помогает пережить кратковременный пик нагрузки.

Пример:

```text
город: Moscow
запрос: GET /hotels?city=Moscow&minStars=4
```

После первого запроса результат находится в кеше, и последующие пользователи получают ответ быстрее.

---

## 2. Как rate limiting улучшает производительность

Rate limiting ограничивает количество запросов к дорогим endpoint'ам.

В проекте ограничен:

```text
POST /bookings
```

Этот endpoint выбран потому, что создание бронирования:

```text
требует авторизации
проверяет доступность номера
обращается к PostgreSQL
выполняет write-операцию
может вызывать конкуренцию за один номер
```

## 2.1 Защита от перегрузки

Без rate limiting пользователь или бот может отправить много запросов на создание бронирования подряд. Это создаст нагрузку на:

```text
HTTP handler
PostgreSQL
проверку конфликтов дат
транзакции создания бронирования
```

С Token Bucket API пропускает только ограниченное количество запросов:

```text
10 запросов в минуту на пользователя
```

Остальные запросы получают:

```text
429 Too Many Requests
```

## 2.2 Защита от ошибочных retry

Клиентское приложение может ошибочно повторять запрос при таймауте. Rate limiting ограничит такие повторные попытки и не позволит им перегрузить систему.

## 2.3 Защита бизнес-операции

Создание бронирования — критичная операция. Rate limiting снижает риск ситуации, когда один пользователь быстро создаёт много конкурирующих броней и мешает другим пользователям.

## 4. Как измерить эффективность кеширования

Основная метрика эффективности кеширования — hit rate.

Формула:

```text
cache_hit_rate = cache_hits / (cache_hits + cache_misses)
```

Пример:

```text
cache_hits = 90
cache_misses = 10

cache_hit_rate = 90 / (90 + 10) = 0.9 = 90%
```

Чем выше hit rate, тем больше запросов обслуживается без обращения к PostgreSQL.

## 4.1 Ручная проверка через HTTP-заголовки

В реализации добавлен заголовок:

```text
X-Cache
```

Возможные значения:

```text
MISS
HIT
```

Проверка:

```bash
curl -i "http://localhost:8080/hotels?city=Moscow&minStars=4"
curl -i "http://localhost:8080/hotels?city=Moscow&minStars=4"
```

Ожидаемый результат:

```text
первый запрос  -> X-Cache: MISS
второй запрос  -> X-Cache: HIT
```

Для номеров:

```bash
curl -i "http://localhost:8080/rooms?hotelId=1"
curl -i "http://localhost:8080/rooms?hotelId=1"
```

Ожидаемый результат:

```text
первый запрос  -> X-Cache: MISS
второй запрос  -> X-Cache: HIT
```

## 4.2 Проверка инвалидации кеша

Для отелей:

```bash
curl -i "http://localhost:8080/hotels?city=Moscow&minStars=4"

curl -i -X POST http://localhost:8080/hotels \
  -H "Content-Type: application/json" \
  -d '{"name":"Test Hotel","city":"Moscow","address":"Test Street 1","stars":4,"description":"Test"}'

curl -i "http://localhost:8080/hotels?city=Moscow&minStars=4"
```

После `POST /hotels` кеш должен быть инвалидирован. Следующий `GET /hotels` должен снова вернуть:

```text
X-Cache: MISS
```

## 4.3 Измерение времени ответа

Можно сравнить время ответа через `curl`:

```bash
curl -o /dev/null -s -w "time_total=%{time_total}\n" \
  "http://localhost:8080/hotels?city=Moscow&minStars=4"

curl -o /dev/null -s -w "time_total=%{time_total}\n" \
  "http://localhost:8080/hotels?city=Moscow&minStars=4"
```

Ожидается, что второй запрос будет быстрее, потому что он обслуживается из кеша.

## 5. Как измерить эффективность rate limiting

## 5.1 Проверка HTTP 429

Для проверки можно выполнить несколько запросов подряд:

```bash
TOKEN="<TOKEN_FROM_LOGIN>"

for i in {1..12}; do
  curl -i -X POST http://localhost:8080/bookings \
    -H "Content-Type: application/json" \
    -H "Authorization: Bearer $TOKEN" \
    -d '{"roomId":1,"checkIn":"2026-12-10","checkOut":"2026-12-11","guestsCount":1}'
done
```

Ожидаемый результат:

```text
первые запросы -> 201 Created или бизнес-ошибка бронирования
после исчерпания лимита -> 429 Too Many Requests
```

## 5.2 Проверка rate limit headers

В ответах должны быть заголовки:

```text
X-RateLimit-Limit
X-RateLimit-Remaining
X-RateLimit-Reset
```

Пример:

```text
X-RateLimit-Limit: 10
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 6
```

Это позволяет клиенту понять:

```text
какой лимит действует
сколько запросов осталось
когда можно повторить запрос
```

## 6. Ожидаемый эффект от оптимизации

## 6.1 До кеширования

```text
каждый GET /hotels обращается к PostgreSQL
каждый GET /rooms обращается к PostgreSQL
при одинаковых запросах база выполняет одну и ту же работу
```

## 6.2 После кеширования

```text
первый запрос обращается к PostgreSQL
повторные запросы в течение TTL обслуживаются из кеша
уменьшается нагрузка на БД
уменьшается среднее время ответа
```

## 6.3 До rate limiting

```text
POST /bookings можно вызывать слишком часто
ошибочные retry могут перегрузить БД
нет защиты от автоматизированных запросов
```

## 6.4 После rate limiting

```text
частота POST /bookings ограничена
дорогие операции защищены
при превышении лимита возвращается 429
клиент получает понятные rate limit headers
```

---

## 7. Итог по шестому пункту

Кеширование и rate limiting улучшают производительность системы по-разному:

```text
кеширование ускоряет частые read-запросы и снижает нагрузку на PostgreSQL
rate limiting защищает дорогие write-запросы и предотвращает перегрузку
```

Для текущего проекта реализованы:

```text
Cache-Aside кеширование:
- GET /hotels
- GET /rooms?hotelId=...

Token Bucket rate limiting:
- POST /bookings
```

Основные метрики эффективности:

```text
cache_hit_rate
http_request_duration_ms
db_queries_total
http_429_total
rate_limit_rejected_total
```

Эти метрики позволяют понять, насколько оптимизации реально помогают системе.
